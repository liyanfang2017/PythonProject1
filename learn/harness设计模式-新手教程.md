# Harness 设计模式：新手入门教程

> 本文是《harness设计模式.md》的精简版。目标：30 分钟理解底层原理，照着模板就能设计出自己的第一个 Harness Skill。

---

## 一、一句话理解 Harness

**Harness 原意是「马具」**——套在马身上、控制方向和力量的一套装置。

AI 就是一匹快马：力气很大，但方向不稳。Harness 设计模式就是给它套上一套结构化的「约束装置」，让它**高效、稳定、准确地**完成复杂任务。

记住这句核心思想：

> **Harness 不是限制 AI，而是给 AI 明确的结构，让它的能量用在对的地方。**

Harness 不是一个固定的技术规范，而是一套**方法论**：凡是能让 AI 运行得更稳定、高效、准确的设计手段，都属于 Harness。

---

## 二、为什么需要它？AI 的三种失控

不用 Harness 时，直接对 AI 说「帮我写个测试」，你大概率会遇到：

| 失控模式 | 表现 |
|---------|------|
| **走错方向** | 做了你没让它做的事，顺手改了一堆无关文件 |
| **中途卸力** | 跳过步骤走捷径——甚至修改测试用例本身来"强行通过" |
| **跑飞收不回来** | 进入无限循环重试，或过度生成停不下来 |

这三种失控不是偶发 bug，而是 LLM 的**天然缺陷**。理解了这一点，就理解了 Harness 四大要素为什么长成那个样子。

---

## 三、底层原理：四个缺陷，四个对策（本文最重要的一章）

Harness 的每个设计，都是针对 LLM 的一个具体缺陷。先记住这张表，后面的所有内容都是它的展开：

| # | LLM 的缺陷 | 对策（Harness 要素） |
|---|-----------|---------------------|
| 1 | 上下文易失：对话会被截断、压缩、遗忘 | **产物契约**：Agent 间靠文件传信息，不靠对话 |
| 2 | 目标漂移：AI 会为"表面达标"而作弊 | **护栏规则** + 独立的验证者 |
| 3 | 注意力有限：一个 Agent 干多件事，质量会下降 | **角色边界**：每个 Agent 只做一件事 |
| 4 | 遇到失败会迷失：不知道下一步，或无限循环 | **状态机**：所有路径（含异常路径）预先画好 |

### 原理 1：上下文是易失的 → 信息外部化到文件

多轮对话中，早期内容会被压缩或丢弃。如果 Agent A 的结论只存在于对话里，Agent B 可能拿到的是残缺版本。

**对策**：让每个 Agent 把结论**写入固定格式的文件**（如 `_analysis.md`），下游 Agent 读文件干活。好处：

- 信息持久、完整，随时可查
- 整个流程**可审查**（人可以打开文件检查）、**可重放**（出问题能回溯是哪一步的产物错了）、**可调试**

### 原理 2：AI 会为"表面达标"而作弊 → 需要禁止清单和独立验证者

AI 优化的是"任务完成"这个表面目标，不是你的真实意图。典型例子：测试跑不过 → AI 直接改测试断言让它通过 → 表面达标，实际啥也没验证。原文作者甚至见过 AI 改需求工单来通过任务的案例。

**对策**：

- **验证者和实现者必须分离**——写代码的 Agent 不能自己宣布"测试通过"，必须由另一个 Agent 独立运行并出具报告
- **明确列出禁止清单**——"不许修改已有函数""不许截断日志""不许跳过审查直接跑测试"。写得越具体，AI 越没有钻空子的空间

### 原理 3：注意力是有限的 → 一个 Agent 只做一件事

让一个 Agent 同时"调研 + 写码 + 跑测试"，它会在不同任务间反复横跳，上下文越堆越多，决策越来越漂。

**对策**：按**能力类型**拆分角色。典型三段式：

- **分析 Agent**：只读代码库，产出分析报告（需要"调研"能力）
- **实现 Agent**：只按报告写代码（需要"编码"能力）
- **验证 Agent**：只跑测试、分析失败（需要"诊断"能力）

每个 Agent 的 prompt 短而聚焦，行为可预测。

### 原理 4：恢复路径必须预设 → 状态机

AI 遇到失败时，如果不告诉它怎么办，它要么瞎猜，要么死循环。

**对策**：把流程画成一张**状态转移图**，正常路径和所有异常路径都预先定义：

```text
START -> 分析 -> 实现 -> 验证 -> 判断
                                |
                                +-> 通过   -> 完成
                                +-> 架构违规 -> 实现(架构修复) -> 验证 -> 判断
                                +-> 运行失败 -> 实现(重试修复) -> 验证 -> 判断
                                +-> 失败超过 N 次 -> 停止，报告给人类
```

三个关键细节：

1. **重试要有上限**（一般 2 次），超过就停下来找人类——3 轮还修不好，说明不是简单修一修能解决的
2. **错误要分类**，不同错误走不同修复模式（架构问题修架构，定位问题改描述），比盲目重试准确率高得多
3. **用户交互节点只留一个**（通常在分析完成后、动手前），其余全自动——问太多次，自动化就没意义了

## 四、动手设计：一个 Harness Skill 的最小结构

一个完整的 Harness Skill 只需要 **3 类文件**：

```text
my-skill/
├── SKILL.md                ← 总控：状态机 + 调度规则（Harness 本体）
├── agents/
│   ├── analyzer.md         ← 分析 Agent 的 prompt
│   ├── implementer.md      ← 实现 Agent 的 prompt
│   └── verifier.md         ← 验证 Agent 的 prompt
└── artifacts/              ← 产物目录（Agent 间的信息中转站）
    ├── _analysis.md        ← 分析 Agent 的输出
    └── _verification.md    ← 验证 Agent 的输出
```

运行时的样子：

```text
用户说需求
    |
[总控 SKILL.md]  —— 它自己不干活，只调度和判断
    |
[分析 Agent] --> 写 _analysis.md --> 展示摘要，用户确认
    |
[实现 Agent] --> 读 _analysis.md --> 写代码
    |
[验证 Agent] --> 审查 + 跑测试 --> 写 _verification.md
    |
[总控读报告判断] --> 通过则结束 / 失败则按错误类型调度修复
```

下面分两步把它写出来。

### 第一步：写总控 SKILL.md（五要素）

| 要素 | 作用 |
|------|------|
| 1. 角色定义 | 告诉主 Agent 它是总控，**不要自己动手实现** |
| 2. 子 Agent 列表 | 每个Agent 的职责、prompt 路径、产物文件 |
| 3. 状态机 | 流程走向 + 跳转条件 + 重试上限 |
| 4. 调度协议 | 每次调度子 Agent 传什么参数 |
| 5. 禁止行为 | 覆盖所有"走捷径"路径的禁止清单 |

**角色定义是整个文件最重要的一段。** 对比：

```markdown
<!-- 反面：模糊。AI 会自己动手写测试，而不是调度子 Agent -->
你是一个帮助用户写测试的 AI 助手。

<!-- 正面：明确职责 + 反向约束 -->
## 你的角色
你是流程总控，职责只有三件事：
1. 调度子 Agent 按正确顺序执行
2. 判断每个 Agent 的输出，决定下一步
3. 保证不跳步、不遗漏、不突破重试上限

默认不要自己写代码、不要自己跑测试，这些工作交给子 Agent。
```

写法要点：**用列表列出"你只有 N 件事"，结尾加一行反向约束，越具体越好，不留模糊空间。**

**状态机部分**必须写清重试计数规则：

```markdown
### 重试计数
- retry 初始值为 0
- 架构类违规不计入重试（代码质量问题，修了就消失）
- 仅当"测试运行失败"时 retry += 1（可能是环境问题，需要限次）
- 最多自动重试 2 次，超过则停止并向用户报告
```

**禁止行为清单**的写法：逐一想象 AI 可能的偷懒路径，每条堵死一个：

```markdown
| # | 禁止 |
|---|------|
| 1 | 跳过分析阶段直接写代码 |
| 2 | 实现后不调用验证 |
| 3 | 主控亲自写代码 / 亲自跑测试 |
| 4 | 失败超过上限后继续自动重试 |
| 5 | Agent 间只口头传话，不写入产物文件 |
```

### 第二步：写子 Agent prompt（五段式）

每个子 Agent 的 prompt 固定五段，缺一不可：

```markdown
# 角色
我是 XX Agent，唯一职责是 [一句话]。

# 输入
[文件路径 / 参数，明确到具体路径]

# 工作流程
1. 第一步……
2. 第二步……
3. ……

# 输出格式
[产物文件的精确模板，用代码块给出]

# 约束
- 绝对不能做的事 [逐条列出]
```

三个 Agent 的设计要点：

**分析 Agent——核心原则：让下游不需要再读源码。**
它产出的 `_analysis.md` 必须完整到实现 Agent 拿到就能写代码（方法签名、import 路径、代码片段都要放进去）。这能加快速度、减少错误，还让用户在确认节点看到清晰的计划。约束示例：不写代码、不跑测试。

**实现 Agent——核心设计：分模式 + 保护已有代码。**
- 按"首次实现 / 修架构 / 修定位 / 修运行失败"分四种模式，每种模式任务不同
- **已有函数保护**（最精妙的设计）：修改任何已存在的函数前必须查审批清单，不在清单里就停下来报告，等用户确认。替代策略是"新增带后缀的新方法，绝不动旧方法"——因为旧方法可能被其他 10 个测试依赖
- 约束示例：first_run 模式下禁止读项目源码，只准用 `_analysis.md`

**验证 Agent——核心原则：先静态审查，再跑测试。**
- 先查代码分层合规（违规立即报告，不浪费时间跑测试）
- 再运行测试，日志**完整保留不截断**（截断的日志会让修复者找不到关键行）
- 失败时输出**错误分类 + 截图分析 + 修复建议**，格式严格，因为总控要读其中的状态字段做判断
- 约束示例：不修改任何源码——验证者绝不能既当裁判又当运动员

## 五、设计时的五个常见陷阱

1. **总控写得太复杂**——SKILL.md 只管"调度 + 判断"，实现细节写进对应 Agent 的 prompt
2. **分析报告太简略**——"代码上下文"章节缺信息，实现 Agent 被迫自己读源码，产物契约形同虚设
3. **验证日志被截断**——完整日志是修复的依据
4. **重试上限太大**——5 次、10 次的重试会让一个问题卡住整个流程，2 次为宜
5. **用户交互节点太多**——理想只有一个确认节点，每步都问用户等于没有自动化

## 六、交付前检查清单

对照下表，每项都打钩才算一个合格的 Harness Skill：

**架构层**
- [ ] 任务拆成了 3 种能力（分析/实现/验证），每个 Agent 一个 prompt 文件
- [ ] 有总控状态机，覆盖正常路径和所有异常路径
- [ ] 重试有上限（2 次），超限停下报告人类
- [ ] 用户确认节点只有一个

**Agent prompt 层（每个 Agent 都要过一遍）**
- [ ] 角色定义清晰，只有一句话职责
- [ ] 输入来源明确到文件路径
- [ ] 工作流程有编号步骤
- [ ] 输出格式有严格模板
- [ ] 有禁止清单防越权

**产物层**
- [ ] Agent 间信息全部通过文件传递，不依赖对话记忆
- [ ] 产物格式固定，总控能读取其中的状态字段做判断

## 七、迁移到你自己的项目

把这套模式搬到任何领域（API 测试、文档生成、数据处理……），只需改五处：

1. **定义你的领域规范**——你项目里"什么是合规"（对应分层架构），Verifier 拿它做静态审查
2. **建最佳实践文档库**——按模块写参考文档 + 关键词映射表，Analyzer 按需读取
3. **更新目录/资源映射**——Analyzer 的"需求类型 → 去哪找"表
4. **更新验证命令**——Verifier 用你项目自己的测试/构建命令
5. **替换领域专用 API**——prompt 里的代码模板换成你的技术栈

判断你的任务适不适合 Harness，看三个特征：**步骤多且分工明确**、**有机器可检查的质量标准**、**失败是常态需要结构化修复**。三者占其二，就值得上 Harness。
