# 从零设计一个 Harness 自动化 Skill：材料清单与落地步骤

> 前置阅读：《harness设计模式-新手教程.md》（四大要素 + 底层原理）。
> 本文回答一个问题：**新手手上只有想法，怎么一步步把它变成一个包含工具调用、子 Agent 调度、文件/外部连接访问的、能跑起来的 Skill？**
> 所有示例基于 Claude Code 的 `.claude/skills/` 结构（本仓库 testcase-generator、api-test-pipeline 均为此结构，可对照参考）。

---

## 全景图：从想法到落地只有四步

```text
[准备材料] --> [画设计图] --> [按步骤实现] --> [测试迭代]
  第 0 章        第 1 章         第 2 章         第 3 章
```

新手最常见的失败方式是**跳过第 0、1 章直接写 SKILL.md**——写出来的东西角色混乱、没有异常路径、产物格式随缘。请按顺序来。

---

## 第 0 章：开工前要准备的材料

把下面四类材料凑齐，才动手写代码。**缺哪类，后面对应的环节就会失控。**

### 0.1 任务定义材料 —— 决定"总控"怎么写

| 材料 | 回答的问题 | 反面后果 |
|------|-----------|---------|
| 一句话任务定义 | 这个 Skill 被调用时到底做什么？ | 角色定义模糊，AI 自己动手不调度 |
| 触发场景清单 | 用户会说什么话来触发？（至少 3 句原话） | 该触发时不触发，不该触发时乱触发 |
| 输入形态清单 | 接受哪些输入？文件/文本/URL/截图？各形态的边界？ | 输入不认识时 AI 硬猜 |
| 期望输出定义 | 输出什么格式？哪些字段必填？落盘到哪？ | 每次输出格式都不一样，下游没法用 |

### 0.2 领域知识材料 —— 决定"分析/实现 Agent"的质量

| 材料 | 用途 |
|------|------|
| 领域规范文档 1~N 份 | 项目分层规则、命名规范、编码规范。放到 `references/`，Agent 按需读取 |
| few-shot 样例 2~3 组 | 完整的"输入 → 期望输出"对照。LLM 模仿样例远比遵守规则可靠 |
| 关键词映射表 | "什么需求 → 读哪份参考文档 / 去哪个目录找"，供分析 Agent 检索用 |
| 相邻真实案例 | 项目里已有的、好的真实产物（已有的测试文件、已有的脚本），供参照风格 |

### 0.3 工具与连接材料 —— 决定"工具调用"环节能不能落地

| 材料 | 说明 | 检查点 |
|------|------|--------|
| 可执行命令清单 | Skill 内部要跑哪些命令/脚本？每个命令的输入、输出、退出码 | 在终端手动跑通过一遍 |
| 机械校验脚本 | 用代码做的合规检查（格式校验、字段校验），退出码约定：`0`=通过，`1`=违规（清单打到 stdout），`2`=传参错误 | 用正常/违规/错误三种输入各测一遍 |
| 外部连接信息 | 要访问的 API 地址、数据库、内网服务；**认证方式**（token/API Key 放环境变量或配置文件，绝不硬编码进 prompt） | 凭证已配置、连通性已验证 |
| 文件访问边界 | 哪些目录可读、哪个目录可写（产物落盘目录），写进 Skill 明确声明 | 产物目录已创建 |
| 环境依赖 | Python 版本、第三方包、系统工具；在 SKILL.md 或 README 里写清 | 新机器上能一键装好 |

### 0.4 验收测试材料 —— 决定你能不能判断"做完了"

| 材料 | 说明 |
|------|------|
| 正常路径用例 1 个 | 标准输入 → 应产出符合格式定义的输出 |
| 边界用例 1 个 | 大体量输入 / 混合来源 / 用户中途改需求 |
| 异常用例 2 个 | 坏文件（损坏 JSON）、缺关键信息、外部连接不通——Skill 应明确报错而不是硬生成 |

### 材料齐备核对单

```text
[ ] 一句话任务定义 + 3 句触发原话
[ ] 输入形态清单（含不支持的形态及引导话术）
[ ] 输出格式定义（字段、必填、落盘路径）
[ ] 领域规范文档已放 references/
[ ] few-shot 样例 2~3 组
[ ] 校验脚本写好且三种输入各测过
[ ] 外部凭证在环境变量，连通性验证过
[ ] 产物目录已建，读写边界已明确
[ ] 验收用例 4 个（正常/边界/异常x2）
```

## 第 1 章：画设计图（动笔前必做）

### 1.1 先判断：这个任务配不配用 Harness？

三个特征占其二，才值得上（否则一个普通 SKILL.md 单 Agent 流程就够）：

1. 步骤多且**能力类型不同**（调研/生成/执行/验证需要不同技能）
2. 有**机器可检查**的质量标准（格式、分层、字段可脚本校验）
3. **失败是常态**，需要"失败 → 分类 → 修复 → 重试"的结构化循环

### 1.2 拆角色：把任务按能力切成 2~4 段

问自己：这件事需要哪几种能力？每种能力一个 Agent。

```text
例：自动化生成 API 测试
  分析能力：读需求 + 检索接口文档  -> Analyzer（explorer 型）
  实现能力：按规范产出产物        -> Implementer（worker 型）
  验证能力：跑校验 + 分析失败     -> Verifier（worker 型）
```

**判断标准：两个阶段若总是由同一批上下文完成、从不需要独立视角，就合并；若一个阶段要"挑另一个阶段的毛病"，必须分开（实现者和验证者绝不能是同一个）。**

### 1.3 画状态机：正常路径 + 所有异常路径

```text
START -> 分析 -> 【用户确认门禁 G1】 -> 实现 -> 校验 -> 判断
                                                   |
                                                   +-> 通过 -> 输出 -> DONE
                                                   +-> 格式违规 -> 实现(修复) -> 校验 -> 判断
                                                   +-> 运行失败 -> 分类错误 -> 实现(对应修复模式) -> 校验 -> 判断
                                                   +-> 失败超过 2 次 -> 停止，报告人类
```

设计时必须回答的四个问题（答不出来就是图没画完）：

1. **哪几处需要用户确认？** 理想只有 1 处（分析后动手前）
2. **失败怎么分类？** 每类错误走不同的修复模式，不盲目重试
3. **重试上限是多少？** 2 次；哪些违规不计入重试（如纯格式问题，修了就消失）
4. **输入不认识/连接不通时怎么办？** 明确报错请求人工，禁止硬生成

### 1.4 定义产物契约：Agent 之间传什么文件

每个跨 Agent 传递的信息都落成文件，格式预先定死：

| 产物 | 生产者 | 消费者 | 关键字段 |
|------|--------|--------|---------|
| `_analysis.md` | Analyzer | Implementer | 需求理解、参考案例、复用计划、**完整代码上下文** |
| `_verification.md` | Verifier | 总控 | 状态字段（通过/违规类型/失败）、错误分类、修复建议 |

原则：**总控只读产物文件做判断，不听任何 Agent 的口头汇报。**

### 1.5 分工：哪些给脚本，哪些给 LLM

一条铁律：**机械的交给脚本，语义的交给 LLM。**

| 判断维度 | 交给谁 | 例子 |
|---------|--------|------|
| 可以用代码精确判定的 | 脚本 | 字段是否必填、ID 格式、JSON 是否合法、枚举值范围 |
| 需要理解语义的 | LLM | 需求理解、内容生成、根因分析、修复建议 |
| 两者都涉及的 | 脚本先跑机械校验，LLM 再做语义审查，**结论合并呈现** | 反编造溯源：字段名回查原文（语义）+ 格式校验（脚本） |

## 第 2 章：按步骤实现（照做即可落地）

### Step 1：建目录骨架

```bash
mkdir -p .claude/skills/my-skill/{references,scripts,artifacts}
touch .claude/skills/my-skill/SKILL.md
```

```text
.claude/skills/my-skill/
├── SKILL.md          <- 总控（第 2~4 步填充）
├── references/       <- 领域规范、few-shot、prompt 模板（按需读取，不塞进 SKILL.md）
├── scripts/          <- 机械校验、解析、检索脚本
└── artifacts/        <- 产物中转站（_analysis.md 等）
```

### Step 2：写 SKILL.md 头部（决定触发）

```markdown
---
name: my-skill
description: 一句话说明做什么+产出什么。然后写触发短语："当用户说'帮我做X'、'把Y转成Z'时使用"。再写不适用边界："不适用：xxx 场景 -> 用 xxx"。description 是路由依据，必须包含触发原话和分流规则。
---
```

description 写法三要素（缺一不可）：

1. **做什么**：能力 + 产出物
2. **触发短语**：用户真实的说法，放 3~5 句
3. **不适用边界**：明确"这种请求去用别的 skill"，防止错误路由

可对照本仓库 `testcase-generator/SKILL.md` 的 description 抄结构。

### Step 3：写总控五要素（SKILL.md 正文）

**要素一：角色定义（最重要的一段）**

```markdown
## 你的角色
你是流程总控，职责只有三件事：
1. 按状态机调度子 Agent 执行
2. 读取产物文件判断每步结果，决定下一步
3. 保证不跳步、不遗漏、不突破重试上限

默认不要自己分析需求、自己写代码、自己跑校验命令——这些交给子 Agent。
```

**要素二：子 Agent 列表（表格，含调度方式与产物）**

```markdown
## 子 Agent
| 阶段 | prompt 文件 | 调度方式 | 职责 | 产物 |
|------|------------|---------|------|------|
| 分析 | agents/analyzer.md | Agent 工具 (subagent_type=Explore) | 读需求+检索文档 | artifacts/_analysis.md |
| 实现 | agents/implementer.md | Agent 工具 (subagent_type=general-purpose) | 按分析结果生成产物 | 产物文件 |
| 验证 | agents/verifier.md | Agent 工具 (subagent_type=general-purpose) | 机械+语义审查、跑校验 | artifacts/_verification.md |
```

agent_type 怎么选：

| 类型 | 适用 |
|------|------|
| 只读探索型（如 Explore） | 分析 Agent：大量读文件、检索，不写任何东西 |
| 全能型（如 general-purpose） | 实现 / 验证 Agent：要写文件、跑命令 |

**要素三：状态机（含重试计数）**

```markdown
## 状态机
START -> ANALYZE -> 【G1 用户确认】 -> IMPLEMENT -> VERIFY -> JUDGE
                                                    |
                                                    +-> PASS -> OUTPUT -> DONE
                                                    +-> FORMAT_VIOLATION -> IMPLEMENT(fix) -> VERIFY -> JUDGE（不计重试）
                                                    +-> FAIL -> IMPLEMENT(retry_fix) -> VERIFY -> JUDGE（计入重试）
                                                    +-> retry > 2 -> 报告失败，停止

重试计数：retry 初始 0；仅 FAIL 时 +1；上限 2 次。
用户交互：仅 G1 一处。G1 不通过则回 ANALYZE 修正。
```

**要素四：调度协议（每次调度传什么，具体到参数）**

```markdown
## 调度总则
1. 调度前先 Read 对应 agent prompt 文件的完整内容
2. 将 prompt 正文 + 用户输入 + 前序产物文件路径 拼进任务描述，通过 Agent 工具发出
3. 等待子 Agent 完成，读取其写入的产物文件（不听口头汇报）
```

**要素五：禁止行为清单（堵死每条偷懒路径）**

```markdown
## 禁止行为
| # | 禁止 |
|---|------|
| 1 | 跳过分析直接实现；实现后不验证 |
| 2 | 总控亲自写内容 / 亲自跑校验 |
| 3 | 校验失败后不分类错误就盲目重试 |
| 4 | 重试超过 2 次继续自动执行 |
| 5 | Agent 间口头传信，不落 artifacts/ |
| 6 | 校验脚本报错时基于残缺输入硬生成 |
| 7 | 未经 G1 确认就开始产出最终文件 |
```

### Step 4：写子 Agent prompt（五段式，一个文件一个 Agent）

```markdown
# 角色
我是 Analyzer，唯一职责：把用户需求转成结构化分析报告，写入 artifacts/_analysis.md。

# 输入
- 用户需求原文（由总控在任务描述中给出）
- references/ 下的规范文档（按关键词映射表选取 1~2 份）

# 工作流程
1. 解析需求，拆成有序步骤
2. 按关键词映射表读取对应 references/ 文档
3. 检索项目中的相邻真实案例，提取可复用模式
4. 对每一步标注：复用 / 扩展 / 新建 / 修改（修改需用户在 G1 审批）
5. 将全部实现所需上下文写入 _analysis.md（方法签名、路径、代码片段必须完整）
6. 在返回消息中报告 _analysis.md 路径与摘要，等待用户确认

# 输出格式
artifacts/_analysis.md，章节固定：原始需求 / 参考资料 / 操作步骤 / 复用计划 / 代码上下文

# 约束
- 不写实现代码、不跑校验、不写最终产物
- "代码上下文"章节必须完整到 Implementer 无需再读项目源码
```

三个 Agent 各自的设计要点（详见《harness设计模式-新手教程.md》第四章）：

- **Analyzer**：产出要完整到下游免读源码；"修改已有文件"必须标出来供审批
- **Implementer**：分模式（首做/修格式/修内容）；**改已有函数前必须查审批清单，不在清单就停下报告**
- **Verifier**：先跑脚本机械校验，再做语义审查；**日志/报告完整不截断**；不修改任何产物——验证者绝不动手改

### Step 5：实现三类"复杂操作"的写法

**A. 工具调用（跑脚本）** —— 在 SKILL.md 中写明精确命令与退出码语义：

```markdown
## 机械校验
将产物的 JSON 表示传入校验脚本：

    cat artifacts/cases.json | python3 .claude/skills/my-skill/scripts/validate.py

退出码：0=全部合规；1=违规（清单打到 stdout，逐条修正后重跑）；2=输入错误。
```

对应脚本的最小骨架（`scripts/validate.py`）：

```python
#!/usr/bin/env python3
"""机械校验：stdin 进 JSON，stdout 出违规清单，退出码 0/1/2。"""
import json, sys

def main():
    try:
        data = json.load(sys.stdin)
    except Exception as e:
        print(f"输入错误: {e}", file=sys.stderr); sys.exit(2)
    errors = []
    for i, item in enumerate(data):
        for field in ("title", "steps", "expected"):   # 按你的格式定义改
            if not item.get(field):
                errors.append(f"第{i}条: 缺必填字段 {field}")
    if errors:
        print("\n".join(errors)); sys.exit(1)
    sys.exit(0)

if __name__ == "__main__":
    main()
```

**B. 文件访问** —— 在 SKILL.md 明确读写边界，产物统一走 artifacts/：

```markdown
## 文件访问规则
- 可读：用户指定的输入文件、references/ 全部、项目源码（仅 Analyzer 与 Verifier）
- 可写：artifacts/ 下的产物文件、用户明确指定的输出路径
- 禁止：修改 artifacts/ 之外任何已有文件（Implementer 修改已有函数须走审批清单）
```

**C. 外部连接访问** —— 凭证进环境变量，连接失败必须走兜底：

```markdown
## 外部接口调用
- 接口地址：从环境变量 MY_API_BASE 读取；凭证从 MY_API_TOKEN 读取
- 禁止在 prompt、产物文件、日志中出现凭证明文
- 连接失败/超时：报告具体错误（地址+失败原因），请求用户提供网络或凭证；禁止用猜测数据代替真实响应
```

```bash
# SKILL.md 中的调用写法（凭证不落盘）
curl -sS -H "Authorization: Bearer $MY_API_TOKEN" "$MY_API_BASE/endpoint"
```

### Step 6：写异常兜底表

把你能想到的异常场景逐条列进 SKILL.md，行为只有一种正确姿势——**报错 + 请求人工，禁止硬生成**：

```markdown
## 异常兜底
| 场景 | 行为 |
|------|------|
| 无任何输入 / 输入形态不支持 | 列出支持的形态请求提供；支持形态不匹配时引导到对应 skill |
| 文件损坏 / 解析失败 | 明确报错（文件名+原因）；禁止基于残缺内容猜测 |
| 两个来源信息冲突 | 不擅自取舍，列入 G1 提问清单请用户裁决 |
| 外部连接不通 / 超时 | 报告地址+错误，请求人工处理；不用假数据顶替 |
| 校验连续 2 次不过 | 停止，呈现违规清单与已尝试的修复，请人工介入 |
```

### Step 7：写质量自检清单（SKILL.md 最后一节）

```markdown
## 输出前自检
1. 机械校验退出码为 0（或违规项已全部修正）
2. 每条产出的关键内容可溯源到输入原文（语义自查）
3. G1 门禁已通过（或用户明确豁免，输出标注"未经人工确认"）
4. 产物已落盘到指定路径，格式与定义一致
5. 全程未发生禁止行为清单中的任何一条
```

## 第 3 章：测试与迭代

用第 0 章准备的 4 个验收用例按顺序跑：

```text
1. 正常路径：标准输入 -> 全流程走完，产物格式正确？
2. 边界：大体量/混合输入 -> 门禁是否触发圈定建议？
3. 异常 a：喂损坏文件 -> 是否明确报错而非硬生成？
4. 异常 b：断开外部连接 -> 是否报告而非编造响应？
```

每个用例跑完检查三件事：

- **状态机走位正确吗？**（有没有跳步、重试有没有超限、门禁有没有拦住该拦的）
- **产物契约被遵守了吗？**（打开 artifacts/ 里的文件，格式与定义一致？）
- **禁止行为被触碰了吗？**（有没有自己动手、口头传信、截断日志）

发现问题的修法：**优先改 SKILL.md 的规则表述（更具体、更可判定），其次改 agent prompt，最后才考虑加脚本**。每轮只改一处，重跑验收，避免改了 A 坏了 B。

## 第 4 章：可直接抄的 SKILL.md 骨架

把下面模板里的方括号替换掉，就是一个能跑的最小 Harness Skill：

````markdown

# [skill-name]

## 你的角色
你是流程总控，职责只有三件事：
1. 按状态机调度子 Agent 执行
2. 读取产物文件判断结果，决定下一步
3. 保证不跳步、不遗漏、不突破重试上限
默认不要自己[实现动作]、自己[验证动作]，交给子 Agent。

## 子 Agent
| 阶段 | prompt 文件 | 类型 | 职责 | 产物 |
|------|------------|------|------|------|
| 分析 | agents/analyzer.md | 只读探索 | [职责] | artifacts/_analysis.md |
| 实现 | agents/implementer.md | 全能 | [职责] | [产物文件] |
| 验证 | agents/verifier.md | 全能 | [职责] | artifacts/_verification.md |

## 状态机
START -> ANALYZE -> 【G1 用户确认】 -> IMPLEMENT -> VERIFY -> JUDGE
  JUDGE: PASS -> 输出 -> DONE
         FORMAT_VIOLATION -> IMPLEMENT(fix) -> VERIFY -> JUDGE（不计重试）
         FAIL -> IMPLEMENT(retry_fix) -> VERIFY -> JUDGE（计入重试，上限 2）

## 机械校验
    cat artifacts/<产物>.json | python3 .claude/skills/[skill-name]/scripts/validate.py
退出码：0=合规；1=违规（stdout 清单）；2=传参错误。

- 可读：[输入文件、references/]

- 禁止：修改其他已有文件

| 场景 | 行为 |
|------|------|
| 输入缺失/不支持 | 列出支持形态请求提供 |

2. 总控亲自实现/亲自跑校验
3. 盲目重试；超过 2 次继续执行

1. 机械校验退出码 0

3. G1 已通过或已标注豁免
````

## 第 5 章：新手最容易踩的八个坑

1. **跳过材料准备直接写 SKILL.md**——结果每个环节都在现场发明规则
2. **description 不写触发原话**——skill 永远不被触发，或该用别的 skill 时被错误触发
3. **总控里写实现细节**——总控只管调度和判断；细节进 agent prompt，参考文档进 references/（按需读取，别塞爆上下文）
4. **产物契约没有固定格式**——下游 Agent 每次都要猜，或者干脆靠对话传信然后失忆
5. **实现者和验证者是同一个 Agent**——自己查自己等于没查
6. **把语义判断压给脚本，或把机械判断压给 LLM**——前者判不了，后者不稳定
7. **异常路径没写**——AI 遇到坏输入就硬编造；兜底表是防编造的最后一道墙
8. **一次改一堆规则**——改完不跑验收用例，坏了都不知道哪次改动弄坏的
