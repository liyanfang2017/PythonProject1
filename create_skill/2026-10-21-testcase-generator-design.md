# testcase-generator Skill 设计规格（Spec）

- **日期**：2026-10-21
- **状态**：待批准（评审中）
- **交付物**：一个 Claude Skill，安装于 `.claude/skills/testcase-generator/`（项目级）

---

## 1. 背景与意图

### 1.1 为什么做

两个目的，按优先级：

1. **练手**：通过一个真实需求完整走一遍「从 0 编写 Claude Skill」的流程，掌握 SKILL.md / references / scripts 的职责划分与门禁式流程的写法。
2. **实用**：现有 skill 无法覆盖「多源输入」场景——需要一个能同时吃 OpenAPI、PRD 文本、技术方案、设计稿的用例生成器，一次产出接口/UI 两个维度的结构化用例。

### 1.2 与现有 skill 的关系（共存分工，已拍板）

| Skill | 定位 | 边界 |
|-------|------|------|
| `business-test-case`（现有，项目级） | 纯需求文档（PDF/DOCX/MD/TXT/HTML）→ 五类用例（功能/边界值/异常/安全/兼容），绑定团队规范 | **不修改、不停用**；PDF/DOCX 需求文档场景继续引导到它 |
| `api-test-pipeline`（现有，项目级） | 需求 + Swagger → 用例 → **pytest 可执行脚本** | 不修改；本 skill 不产出脚本，脚本需求引导到它 |
| `testcase-generator`（本 spec） | **多源输入 → 结构化用例（仅用例）**，接口/UI 两维 | 与前两者解耦，不引用它们的规范文件 |

分工裁决规则（按「要什么」裁决，不按文件格式裁决）：

- 要**五类分类**（功能/边界值/异常/安全/兼容），或输入为 PDF/DOCX/HTML → business-test-case（本 skill 不解析这些格式）
- 要**可执行脚本** → api-test-pipeline
- 要**三分类（正向/反向/边界）+ 接口/UI 维度**，或输入含 OpenAPI / 技术方案 / 设计稿 → 本 skill
- 模糊请求（如裸「帮我生成测试用例」+ MD/TXT 需求文档）→ 默认本 skill

此规则写入 SKILL.md 的「不适用场景」一节，并作为 description 的路由依据。

## 2. 目标 / 非目标 / 反目标

### 2.1 目标

- G1 支持四种输入来源：OpenAPI/Swagger 文档、需求 PRD 文本、技术方案文档、设计稿（详见 §4）
- G2 产出标准结构化用例，每条含 9 个字段（详见 §5.1）
- G3 流程中设 3 道人工门禁，支持豁免（详见 §6.2）
- G4 双触发：斜杠 `/testcase-generator` + 自然语言短语（详见 §7）
- G5 输出格式三选一：Markdown 表格 / JSON / CSV（详见 §5.2）
- G6 反编造：接口字段、页面控件必须溯源到输入原文（详见 §6.4）
- G7 异常兜底：空输入、文件损坏、信息不足时明确提示，绝不硬生成（详见 §6.5）

### 2.2 非目标（不做的）

- 不产出可执行自动化脚本（pytest / Playwright 等）——「自动化用例」字样按用例描述理解
- 不接入用例管理平台（TestLink / 禅道 / Excel 模板导出等）
- 不修改现有两个 skill；不引用团队规范文档
- 不访问网络（不 fetch 任何 URL，包括 Figma 链接）
- 不做用例的执行、回归、统计

### 2.3 反目标（出现即失败）

- **编造**：用例中出现输入文档里不存在的接口字段名或页面控件名
- **臆测**：信息不足时不提问、静默编造补全
- **门禁失效**：未获确认就推进阶段，且输出中无「未经门禁」标注
- **敏感数据落盘**：把业务数据写入 memory、CLAUDE.md 或输出文件之外的任何持久化位置

## 3. 约束

| # | 约束 | 说明 |
|---|------|------|
| C1 | 只做用例生成 | 唯一交付物是用例集（对话呈现 + 可选文件） |
| C2 | 权限最小化 | 允许：Read 本地文件（文档/图片）、Write 输出文件。禁止：WebFetch/WebSearch、执行网络命令 |
| C3 | 不存储业务敏感数据 | 会话结束不遗留任何业务内容；输出文件是唯一落盘物 |
| C4 | 字段枚举封闭 | 用例类型仅 正向/反向/边界；维度仅 接口/UI；优先级仅 P0/P1/P2 |
| C5 | 环境假定 | macOS + Python 3（脚本仅用标准库，与现有 skill 一致） |

## 4. 输入规范

| 输入来源 | 接受形态 | 解析要点 | 产出维度 |
|---------|---------|---------|---------|
| **OpenAPI 文档** | 本地文件，Swagger 2.0 / OpenAPI 3.x，JSON 或 YAML | 端点清单、参数（in/type/required）、请求体 schema、响应定义、错误码；`$ref` 需展开 | 接口 |
| **需求 PRD 文本** | 本地 MD/TXT 文件，或对话直接粘贴的文本 | 业务背景、功能点、业务规则、角色权限、验收标准 | UI |
| **技术方案文档** | 本地 MD/TXT 文件 | 技术变更点、表结构/状态机、性能与降级约束 | 接口（以技术变更点提取） |
| **设计稿** | 对话内粘贴的截图，或本地 PNG/JPG 图片 | 可见控件（按钮/输入框/列表/文案）、页面结构、状态提示 | UI |

边界规则：

- Figma / 墨刀等**在线设计链接不支持**（违反 C2）；用户给出链接时，请其导出截图或描述页面
- PDF/DOCX 需求文档不支持，引导至 business-test-case
- 混合输入：多来源同时给出时**一次生成**，两维度都覆盖；做交叉溯源（§6.4）
- 未声明来源类型时，按特征自动识别并报给 G1 门禁确认，禁止猜测

## 5. 输出规范

### 5.1 用例字段（9 个，全部必填，顺序固定）

| # | 字段 | 规则 |
|---|------|------|
| 1 | 用例ID | `TC_模块英文大写缩写_三位序号`，如 `TC_LOGIN_001`；模块缩写对照表在 G2 门禁确认；全局不重复 |
| 2 | 模块 | 中文模块名，如「登录」 |
| 3 | 标题 | 具体可验证的动作+结果；无输入依据的场景标题尾注【需确认】 |
| 4 | 前置条件 | 进入用例前必须满足的状态 |
| 5 | 操作步骤 | 一步一个操作，`→` 分隔；接口用例写明方法+路径+关键参数 |
| 6 | 预期结果 | 具体可验证；**禁止**「正常」「无报错」「功能正常」类空泛表述 |
| 7 | 优先级 | P0=核心主流程（失败不可上线）/ P1=重要分支与异常 / P2=边缘与展示类 |
| 8 | 用例类型 | 正向（成功路径）/ 反向（异常输入、错误操作、失败路径）/ 边界（长度/数量/数值/时间/状态边界） |
| 9 | 用例维度 | 接口 / UI |

### 5.2 输出格式与落盘

| 格式 | 结构 |
|------|------|
| **Markdown（默认）** | 统计摘要（总数/类型/维度/优先级分布）→ 用例表格（9 列）→【需确认】清单 |
| **JSON** | 9 字段对象数组，UTF-8，键名用英文（id/module/title/preconditions/steps/expected/priority/case_type/dimension） |
| **CSV** | 首行表头=9 个中文字段名，UTF-8 **带 BOM**（保证 Excel 直开不乱码），字段内换行用引号转义 |

落盘规则：

- 默认写入 `./output/testcases.<md|json|csv>`；用户指定路径则用用户路径
- Markdown 文件与对话呈现一致（统计摘要 + 用例表 + 需确认清单）；**JSON / CSV 为纯数据文件**（JSON 即 §5.1 九字段的对象数组），统计摘要与【需确认】清单仅出现在对话与 Markdown 中
- 每种格式可独立选择；一次运行只产出一种格式（用户可连续要第二种，不重新生成）

## 6. 工作流程

### 6.1 主流程

```
Step 0 收集输入与来源识别 → 【G1 输入理解门禁】
  → Step 1 可测点提取（分维度）→ 【G2 覆盖范围门禁】
  → Step 2 用例生成（维度×类型矩阵）
  → Step 3 反编造自查（溯源校验）
  → 【G3 输出门禁】→ Step 4 按格式输出
```

### 6.2 门禁（3 道）

| 门禁 | 时机 | 呈现内容 | 通过标准 | 不通过时 |
|------|------|---------|---------|---------|
| **G1 输入理解** | Step 0 后 | 来源识别结果与依据、每个来源的理解摘要、**缺失信息提问清单** | 用户确认来源与理解无误、补齐提问 | 按澄清重做 Step 0 |
| **G2 覆盖范围** | Step 1 后 | 模块清单（中文+英文缩写对照）、可测点清单（按维度分组）、生成计划（预计用例量级） | 用户确认无遗漏、粒度合适 | 增删改后重新提交 |
| **G3 输出确认** | Step 3 后、落盘前 | 用例统计、【需确认】用例逐条清单、反编造自查结论（溯源覆盖情况） | 用户确认可输出 | 修正后重新提交 |

强制触发（满足任一条，对应门禁不得跳过）：

- 任一来源无法识别 / 文件解析失败 → 触发 G1
- 可测点少于 3 个，或模块无法给出合理英文缩写 → 触发 G2
- 存在【需确认】用例，或溯源自查发现无出处项 → 触发 G3 并逐条呈现

**豁免规则**：用户明确说「跳过确认 / 全自动执行」方可跳过对应门禁。

**豁免与强制触发的优先级（豁免优先，实质不降级）**：强制触发条件在豁免模式下**不阻断流程**，但其对应的实质动作全部保留——缺失信息提问清单、【需确认】用例清单、溯源存疑清单并入最终输出呈现；反编造删改（删除无出处表述 / 标注【需确认】）照常执行并记录。跳过 G3 时最终输出必须标注「本次未经人工门禁确认」。

### 6.3 生成矩阵（Step 2）

- **接口维**（输入含 OpenAPI/技术方案时）：每个端点至少覆盖 正向×1 + 反向×1 + 边界×1（有 required 字段/长度/枚举约束时）；错误码定义存在时反向用例覆盖主要错误码
- **UI 维**（输入含 PRD/设计稿时）：每个可测点至少 正向×1 + 反向×1；输入框/长度限制存在时补边界
- 核心主流程（P0）每个模块 1-3 条；总用例量随输入规模浮动，不做硬性配额

**覆盖范围默认**：G2 必须呈现完整端点/可测点清单与预计用例量级。端点 > 20 或预估用例 > 100 时，G2 必须主动给出按 tag/模块圈定子集的建议并等待用户圈定，再进入 Step 2；用户坚持全量则按全量执行。大体量 OpenAPI 采用分节读取；可选复用 api-test-pipeline 的解析脚本（`scripts/swagger_parser.py`）作为优化，但不得构成硬依赖（skill 脱离本项目仍应可用）。

### 6.4 反编造机制（本 skill 的质量核心）

**生成时规则**：

- 接口维用例中出现的每个**字段名/参数名/枚举值**，必须能在 OpenAPI 原文（该端点定义）中找到
- UI 维用例中出现的每个**控件名/按钮文案/提示文案**，必须能在设计稿可见元素或 PRD 原文中找到
- 找不到出处：不造词；在 G1/G2 提问清单中列出，请用户补充；用户未补充则该场景不生成，或标题标【需确认】

**自查步骤（Step 3，生成后、G3 前）**：

1. 逐用例抽取其中所有字段名/控件名，回查输入原文
2. 产出溯源结论：可溯源用例数 / 存疑用例数（无出处的字段或控件清单）
3. 存在无出处项 → 删除该表述或整条标【需确认】，并列入 G3 呈现内容

### 6.5 异常兜底

| 场景 | 行为 |
|------|------|
| 无任何输入 | 列出四种支持的输入及各自接受的形态，请求提供；不生成任何用例 |
| 文件不存在 / 无法读取 / 解析失败（如损坏的 JSON） | 明确报错（文件名 + 失败原因），请求重新提供；**禁止**基于残缺内容猜测生成 |
| OpenAPI 缺关键定义（如无 responses、schema 引用断裂） | 列出缺失项提问；用户补不齐的部分，相关用例标【需确认】或不生成该端点 |
| 设计稿图片无法读取 / 内容不可辨认 | 说明情况，请求更清晰的截图或文字描述；不凭模糊轮廓猜控件 |
| PRD 与设计稿冲突（控件/规则不一致） | 不擅自取舍，将冲突点列入 G1 提问清单，请用户裁决 |

## 7. 触发方式

1. **斜杠调用**：`/testcase-generator`（安装后自动可用）
2. **自然语言触发**：以下说法应自动唤起（写入 SKILL.md 的 description）：
   - 「帮我生成测试用例」
   - 「基于这个页面生成测试用例」
   - 「基于这个接口生成用例」
   - 「根据这个 swagger/PRD/设计稿 出用例」

description 编写要求：包含「做什么（多源输入生成结构化测试用例）+ 何时用（给出 OpenAPI/PRD/技术方案/设计稿时）+ 触发短语原话」；同时写入不适用边界（要脚本 → api-test-pipeline；PDF/DOCX 五类用例 → business-test-case）。

## 8. Skill 结构设计（练手重点）

```
.claude/skills/testcase-generator/
├── SKILL.md                  # 主文件（目标 <400 行）
├── references/
│   ├── input-guide.md        # 四类输入的识别特征、解析要点、常见坑（含 OpenAPI $ref 展开规则）
│   └── case-examples.md      # 维度×类型的 few-shot 示例用例集（好例 vs 反例对照）
└── scripts/
    └── validate_cases.py     # 结构校验脚本（纯标准库）
```

**职责划分准则**（写进 SKILL.md 头部注释，供学习）：

| 内容类型 | 去处 | 本例对应 |
|---------|------|---------|
| 需要每次加载的流程、规范、门禁规则 | SKILL.md 正文 | 主流程、9 字段规范、G1-G3 |
| LLM 才能做的判断类指令 | SKILL.md 正文 | 反编造溯源、空泛预期识别 |
| 固定规则的机械校验 | scripts/ | validate_cases.py：必填字段齐全性、枚举合法性、ID 正则 `^TC_[A-Z0-9]+_\d{3}$`、步骤含 `→`；输出违规清单 |
| 按需才读的长参考材料 | references/ | 输入解析细节、示例用例集 |

`validate_cases.py` 的定位：Step 3 自查的**机械部分**由脚本执行，校验对象是规范用例集的 JSON 表示（与 §5.2 输出同构的对象数组）——**默认从 stdin 读入**（Agent 将待校验用例集管道传入），亦接受一个文件路径参数；**不产生任何中间落盘文件**（与约束 C3 一致）。输出违规清单：必填字段缺失、枚举非法、ID 不匹配 `^TC_[A-Z0-9]+_\d{3}$`、步骤缺 `→` 分隔。MD/CSV 由校验通过的同一份结构渲染；验收标准 3 中三种格式的解析自检由 Agent 在 G3 后执行。**语义部分**（溯源、空泛预期识别）由 Agent 按 SKILL.md 指令执行，两类结论合并进 G3。

## 9. 验收标准

1. 给一份真实 OpenAPI 文档，生成接口维用例：抽查 10 条，字段/参数名 100% 可在原文找到
2. 给 PRD + 设计稿混合输入：UI 维用例控件名 100% 溯源；一次产出两维用例
3. 三种格式输出均可被程序解析（`json.load` / csv 读回 / Markdown 表格渲染正常；CSV 含 BOM）
4. 兜底路径各触发一次并符合 §6.5：空输入、损坏 JSON、不可辨认截图
5. 三道门禁按 §6.2 执行；说「跳过」后豁免生效且输出带标注
6. 两种触发方式均可唤起；「要脚本」的请求被正确引导到 api-test-pipeline

- 多语言界面 / i18n 用例
