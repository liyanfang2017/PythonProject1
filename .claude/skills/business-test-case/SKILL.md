# 业务测试用例生成技能

## 概述

本技能指导 Agent 直接从需求文档中自动生成结构化的业务测试用例。整个过程由 Agent 自主完成，不依赖任何外部项目代码。

**核心流程**：
```
读取并识别文档 → 【G1 门禁】→ 提炼功能点 → 【G2 门禁】→ [逐功能点循环生成用例] → 审查 → 【G3 门禁】→ 输出用例文档
```

## 团队规范（强制）

生成用例必须遵循团队规范文档：`/Users/lyf/PycharmProjects/PythonProject1/claudecode测试用例生成/TEAM_STANDARD_测试用例编写规范.md`（v2.0，owner：测试负责人）。执行中若发现本技能描述与规范冲突，**以团队规范为准**。

| 规范条目 | 要求 |
|---------|------|
| 用例分类 | 必须覆盖：功能测试、边界值测试、异常测试、安全测试、兼容性测试（无对应场景可跳过） |
| 必含字段 | 用例ID、用例标题、优先级、前置条件、测试步骤、预期结果 |
| ID 命名 | `TC_模块英文大写缩写_三位数字序号`，如 TC_LOGIN_001、TC_ORDER_001 |
| 优先级 | 仅 P0/P1/P2 三级 |
| 质量红线 | 禁止空泛预期（"系统正常/页面无报错/功能正常"）；一步一个操作；禁止遗漏边界值；无业务依据的场景标题后标注【需确认】 |
| 自检清单 | 用例末尾必须附覆盖率自检清单 |
| 输出顺序 | 简短测试策略说明 → Markdown 表格用例 → 覆盖率自检清单 |

下文各步骤已按上述规范实现。

## 人工门禁（强制）

全流程设置 3 道人工判断门禁。到达门禁时必须暂停，将门禁内容呈现给用户并等待确认；用户要求调整时，回到对应步骤重做后重新过门禁。禁止未经门禁确认直接推进到下一阶段。

| 门禁 | 所处环节 | 呈现给用户的内容 | 通过标准 | 不通过时 |
|------|---------|----------------|---------|---------|
| **G1 文档识别门禁** | Step 1 完成后 | 文档类型判定结果与识别依据、文档理解摘要 | 用户确认类型与理解无误 | 按用户澄清重做 Step 1 |
| **G2 功能点门禁** | Step 2 完成后 | 功能点清单（name/description/related_requirements）及数量统计 | 用户确认无遗漏、粒度合适 | 按意见增删改后重新提交确认 |
| **G3 输出门禁** | Step 4 完成后、写入文件前 | 审查结论、用例统计（总数/类型分布/优先级分布）、【需确认】用例逐条清单 | 用户确认可输出 | 按意见修正后重新提交 |

**强制触发条件**（满足任一条，对应门禁不得跳过）：
- 文档类型无法识别或识别依据不足 → 触发 G1
- 功能点数量 < 3 或 > 20 → 触发 G2，并向用户提示粒度问题
- 用例集中存在【需确认】用例 → 触发 G3，须逐条请用户补充业务依据或确认保留
- 用例集中 P0 数量为 0 → 触发 G3，提示可能漏识别核心主流程

**豁免**：仅当用户明确表示"跳过确认/全自动执行"时方可跳过对应门禁；跳过 G3 时必须在最终输出中标注"本次未经输出门禁人工确认"。

## 工作流程

### Step 1: 读取并理解文档

**输入**：用户提供的文档路径（PDF/DOCX/MD/TXT/HTML），可能是需求文档、接口文档或技术方案文档

**操作**：
1. 使用 `read` 工具读取文档内容。若文档格式不支持直接读取（如 PDF、DOCX），使用 `look_at` 工具提取文字内容。
2. 识别以下关键信息：
   - 业务背景与目标
   - 功能模块划分
   - 业务流程与规则
   - 约束条件与边界
   - 角色与权限
3. 按「文档类型识别规范」判定文档类型，记录识别依据。判定结果决定 Step 2 的提取口径与 Step 3 的生成侧重点。

**文档类型识别规范**：

逐条比对特征，命中该类型特征 ≥ 2 条即判定为该类型；同一文档包含多种类型内容时按章节分别判定；无法判定或依据不足时触发 G1 门禁向用户确认，不得猜测。

| 文档类型 | 识别特征（满足 ≥2 条判定） | 典型关键词 | 对后续步骤的影响 |
|---------|---------------------------|-----------|----------------|
| **需求文档** | ① 有业务背景/目标/用户角色描述 ② 有业务流程或业务规则 ③ 有功能描述或验收标准 | 需求、背景、目标、用户故事、角色、业务流程、验收标准、PRD | Step 2 按业务场景提取功能点；Step 3 五类用例全量覆盖，以业务场景为主线 |
| **接口文档** | ① 有接口清单（URL + HTTP 方法） ② 有请求/响应参数表（字段、类型、必填） ③ 有状态码/错误码定义 | 接口、API、URL、GET/POST/PUT/DELETE、入参、出参、请求体、响应体、错误码 | Step 2 按接口/接口组提取功能点；Step 3 重点生成参数校验（必填/类型/长度/枚举/默认值）、错误码、越权与注入类安全用例，用接口组合还原主流程 |
| **技术方案文档** | ① 有架构/技术选型描述 ② 有表结构(DDL)、状态机或时序图 ③ 有性能/容量/降级/灰度等非功能约束 | 架构、选型、表结构、DDL、时序、缓存、MQ、灰度、降级、QPS、部署 | Step 2 按技术变更点/风险点提取功能点；Step 3 从技术约束提取边界值（字段长度、超时/重试）、异常场景（依赖失败、降级）、兼容场景（灰度、新老版本）；业务验收标准缺失的用例必须标【需确认】 |

**输出**：文档类型判定结果（类型 + 识别依据）+ 对文档的完整理解。输出后提交 **G1 文档识别门禁**，用户确认后方可进入 Step 2。

### Step 2: 提取功能点

**目标**：将需求拆解为可测试的功能场景。

**操作**：
1. 基于 Step 1 的理解，调用 LLM 提取功能点列表。
2. 每个功能点包含：

| 字段 | 说明 | 示例 |
|------|------|------|
| `name` | 功能场景名称 | "打卡规则配置" |
| `description` | 详细描述 | "管理员可以新增、编辑、删除打卡规则" |
| `related_requirements` | 关联的需求原文 | "管理员可在后台配置打卡规则，包括名称、时间、范围..." |

**拆分原则**：
- 每个功能点应是**用户可感知的一个具体操作**
- 功能场景数量建议 **5-15 个**，覆盖全面
- 典型分类纬度：基础数据维护 → 核心业务流程 → 异常处理 → 报表查询
- 粒度适中：太粗则用例集不完整，太细则管理成本高
- 同步识别安全（权限越权、注入等）与兼容性（浏览器、终端适配）相关需求，供 Step 3 生成安全/兼容性用例时引用
- 按文档类型调整提取口径（见 Step 1 识别规范）：需求文档按业务场景提取；接口文档按接口/接口组提取；技术方案文档按技术变更点/风险点提取（如新增表、状态流转、降级策略）

**输出**：功能点列表（Python list of dicts），包含 name/description/related_requirements。输出后提交 **G2 功能点门禁**，用户确认后方可进入 Step 3。

### Step 3: 逐功能点生成测试用例（循环）

**目标**：对每个功能点，依次生成测试用例。

**操作**：
对每个功能点，执行以下循环（生成侧重点按 Step 1 判定的文档类型执行）：

```
for each feature in features:
    1. 调用 LLM，传入功能点信息和文档上下文
    2. LLM 返回该功能点的测试用例列表
    3. 累加到结果集
    4. 进入下一个功能点
```

**每轮循环生成规范（按团队规范用例分类，无对应场景的类别可跳过）**：

| 用例类型 | 说明 | 要求 | 典型优先级 |
|---------|------|------|-----------|
| **功能测试** | 主流程、正向业务路径，操作成功 | 必须覆盖 | P0/P1 |
| **边界值测试** | 字段长度边界、数值上下限、时间边界、状态边界 | 必须覆盖 | P1/P2 |
| **异常测试** | 错误参数、业务异常、网络异常、资源不存在 | 必须覆盖 | P1/P2 |
| **安全测试** | 权限越权、注入攻击、敏感信息泄露、暴力破解防护 | 有对应场景时必须覆盖 | P1/P2 |
| **兼容性测试** | 浏览器、客户端版本、终端适配（H5/APP 项目） | 有对应场景时必须覆盖 | P2 |

每个功能点至少 3 条用例（功能×1 + 异常×1 + 边界值×1）；核心功能（用户高频使用的主流程）建议 **5-10 条**用例。

**每条用例的字段结构**：

```python
{
    "id": "TC_RULE_001",           # 用例编号，格式 TC_模块英文大写缩写_三位数字（必填）
    "name": "管理员成功新增打卡规则",  # 用例标题；无业务依据的场景标题后标注【需确认】（必填）
    "type": "功能测试",             # 用例类型：功能测试/边界值测试/异常测试/安全测试/兼容性测试
    "priority": "P0",              # 优先级：P0/P1/P2（必填）
    "preconditions": "管理员已登录企业管理后台",  # 前置条件（必填）
    "steps": "点击打卡规则→点击新增规则→填写信息→点击保存",  # 测试步骤，→分隔，一步一个操作（必填）
    "test_data": "规则名称=工作日打卡, 打卡时间=09:00-18:00",  # 测试数据（可选）
    "expected": "提示“保存成功”，规则列表新增一行，名称与打卡时间和录入一致",  # 预期结果（必填），禁止空泛描述
}
```

**LLM 调用提示词模板**：

```
你是一个测试用例设计专家。根据功能点生成测试用例，严格遵循团队测试用例编写规范。

功能点名称：{feature.name}
模块英文缩写：{module_abbr}（全大写，如登录模块 LOGIN、订单模块 ORDER）
需求描述：{feature.related_requirements}
功能描述：{feature.description}

要求：
1. 用例分类：功能测试(主流程正向)、边界值测试、异常测试必须覆盖；安全测试(权限越权/注入/敏感信息)、兼容性测试(浏览器/终端适配)视场景补充；无对应场景的类别可跳过
2. 用例编号格式：TC_{module_abbr}_001, TC_{module_abbr}_002...
3. 优先级仅 P0/P1/P2：P0=核心主流程(失败则版本不可上线)/P1=重要分支场景/P2=边缘场景、UI展示、低概率异常
4. steps 一步一个操作，用 → 分隔，禁止一步包含多个操作
5. expected 必须具体可验证，禁止“系统正常、页面无报错、功能正常”等空泛描述
6. 没有业务依据的场景，用例标题后标注【需确认】
7. 输出 JSON 格式：{{"feature": "{feature.name}", "test_cases": [...]}}
```

### Step 4: 审查测试用例集

**目标**：对生成的完整用例集进行质量检查。

**操作**：
1. 合并所有功能点的用例
2. 检查以下维度：

| 审查维度 | 检查内容 | 操作 |
|---------|---------|------|
| **完整性** | 是否覆盖所有功能点；功能/边界值/异常用例是否齐备，安全/兼容性场景是否按需覆盖 | 补充遗漏场景 |
| **质量红线** | 预期是否空泛；步骤是否一步一个操作；边界值是否有遗漏；无业务依据场景是否标注【需确认】 | 逐条修正 |
| **正确性** | 用例步骤和预期是否合理 | 修正逻辑错误 |
| **去重** | 是否存在重复用例 | 合并冗余 |
| **规范性** | ID 是否符合 TC_模块缩写_三位数字、必含字段是否齐全、格式是否统一 | 调整格式 |

3. 调用 LLM 进行审查：

**审查提示词模板**：

```
你是一个测试用例评审专家。审查以下测试用例集，重点检查团队规范质量红线。

审查维度：
1. 质量红线：预期结果空泛（“系统正常/页面无报错/功能正常”）、一步包含多个操作、遗漏边界值场景、无业务依据场景未标注【需确认】——发现即修正
2. 去重：合并重复用例
3. 补充：补充遗漏场景（含安全、兼容性场景）
4. 修正：修正表述不清或逻辑错误的用例

输出 JSON 格式：
{
  "verdict": "通过/需改进",
  "issues": [
    {"description": "问题描述", "suggestion": "修改建议"}
  ]
}
```

### Step 5: 输出用例文档

**目标**：Step 4 审查完成后提交 **G3 输出门禁**，用户确认后将最终用例集输出为结构化 YAML 文件，并按团队规范呈现测试策略说明、Markdown 用例表和覆盖率自检清单。

**输出路径**：用户指定的路径，或默认的 `./output/testcases.yaml`

**YAML 格式规范**：

```yaml
# 文件编码: UTF-8
# 缩进: 2 空格
# 排序: 按功能点名称排序，用例按编号排序

strategy: ...                    # 测试策略说明（简短，规范要求先输出策略）
verdict: 通过                    # 审查结论
issues:                          # 审查问题列表，可为空
  - description: "..."           # 问题描述
    suggestion: "..."            # 修改建议
features:                        # 功能点列表
  - feature: 打卡规则配置          # 功能点名称
    test_cases:                  # 用例列表
      - id: TC_RULE_001
        name: 管理员成功新增打卡规则
        type: 功能测试
        priority: P0
        preconditions: 管理员已登录企业管理后台
        steps: 点击打卡规则→点击新增规则→填写规则信息→点击保存
        test_data: 规则名称=工作日打卡, 打卡时间=09:00-18:00
        expected: 提示“保存成功”，规则列表新增一行，名称与打卡时间和录入一致
      - id: TC_RULE_002
        name: 新增规则时必填项为空
        type: 异常测试
        priority: P1
        preconditions: 管理员已登录企业管理后台
        steps: 点击打卡规则→点击新增规则→不填写规则名称→点击保存
        test_data: 规则名称=""
        expected: 系统提示规则名称不能为空，保存失败
coverage_checklist:              # 覆盖率自检清单（团队规范要求末尾必须附上）
  - item: 正向主流程用例是否覆盖
    result: 是
  - item: 输入字段边界值是否覆盖
    result: 是
  - item: 失败、异常场景是否覆盖
    result: 是
  - item: 权限与安全场景是否覆盖
    result: 是
  - item: 是否存在遗漏的业务规则
    result: 无
```

**写入操作**：
```python
import yaml

output_data = {
    "strategy": strategy,
    "verdict": verdict,
    "issues": issues,
    "features": features_with_cases,
    "coverage_checklist": coverage_checklist,
}

with open(output_path, "w", encoding="utf-8") as f:
    yaml.dump(output_data, f, allow_unicode=True, sort_keys=False, indent=2, width=120)
```


**结果展示顺序（团队规范第七条）**：向用户呈现最终结果时，按以下顺序输出：
1. 简短测试策略说明
2. Markdown 表格用例
3. 覆盖率自检清单

## 优先级定义标准（团队规范）

| 级别 | 定义 |
|------|------|
| **P0** | 核心业务主流程，失败则该版本不可上线 |
| **P1** | 重要分支场景，失败造成用户无法使用次要功能 |
| **P2** | 边缘场景、UI 展示、低概率异常问题 |

## 全流程集成 Prompt（一次性执行）

若用户希望一步完成，可使用以下完整 prompt 驱动 LLM：

```
你是一个专业的需求分析和测试设计专家。

请根据以下需求文档内容，完成以下任务：

## 任务说明

### 阶段一：需求分析与功能点提取
- 阅读并理解文档内容
- 识别业务背景、功能模块、流程规则和约束条件
- 将需求拆分成5-15个具体的、可测试的功能场景
- 每个功能点包含：name(场景名称)、description(详细描述)、related_requirements(需求原文)

### 阶段二：逐功能点生成测试用例
对每个功能点：
- 按团队规范五类分类生成：功能测试(主流程正向)、边界值测试、异常测试必须覆盖；安全测试、兼容性测试视场景补充，无对应场景可跳过
- 用例编号格式：TC_模块英文大写缩写_三位数字，如 TC_LOGIN_001
- 每条用例包含：id、name、type、priority(仅P0/P1/P2)、preconditions、steps(一步一个操作，→分隔)、test_data(可选)、expected
- 质量红线：expected 禁止“系统正常/页面无报错/功能正常”等空泛描述；禁止遗漏边界值场景；无业务依据的场景标题后标注【需确认】

### 阶段三：审查与输出
- 审查用例集的完整性、正确性和规范性（含团队规范质量红线检查）
- 按顺序输出：简短测试策略说明 → Markdown 表格用例 → 覆盖率自检清单

## 输出格式
Markdown 呈现：策略说明 + 用例表格 + 覆盖率自检清单。
同时输出 YAML，包含以下结构：
- strategy: 测试策略说明
- verdict: 审查结论
- issues: 问题列表
- features: 功能点及其测试用例
- coverage_checklist: 覆盖率自检清单
```

> 注意：即使使用一次性 prompt 驱动，G1/G2/G3 三道人工门禁仍须由 Agent 在各阶段之间执行，不得省略。

## 质量检查清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 功能点数量 | 5-15 个 |
| 2 | 每个功能点用例数 | ≥ 3 条 |
| 3 | 用例类型覆盖 | 功能/边界值/异常必选；安全/兼容性视场景覆盖 |
| 4 | 用例编号 | TC_模块英文大写缩写_三位数字，模块内连续不重复 |
| 5 | 优先级分配 | 仅 P0/P1/P2，核心主流程为 P0 |
| 6 | 步骤清晰度 | 一步一个操作，可执行，无歧义 |
| 7 | 预期结果 | 具体可验证，无“系统正常/页面无报错/功能正常”等空泛描述 |
| 8 | 质量红线 | 边界值场景无遗漏；无业务依据场景标题后标注【需确认】 |
| 9 | 输出顺序 | 策略说明 → Markdown 表格 → 覆盖率自检清单 |
| 10 | YAML 格式 | 合法，缩进正确，UTF-8 无乱码 |
| 11 | 门禁执行 | G1/G2/G3 均已通过，或经用户明确豁免并标注 |

## 故障处理

| 问题 | 处理方式 |
|------|---------|
| 文档无法直接读取 | 使用 `look_at` 工具提取文本 |
| 文档类型无法判定 | 触发 G1 门禁，请用户指定文档类型 |
| 功能点过多/过少 | 检查粒度：过细则合并，过粗则拆分 |
| LLM 返回非 JSON | 尝试重新生成，或手动提取 JSON 部分 |
| YAML 输出乱码 | 确保 file encoding 为 utf-8 |
