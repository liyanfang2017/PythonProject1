# 业务测试用例生成技能

## 概述

本技能指导 Agent 直接从需求文档中自动生成结构化的业务测试用例。整个过程由 Agent 自主完成，不依赖任何外部项目代码。

**核心流程**：
```
读取需求文档 → 分析提炼功能点 → [逐功能点循环生成用例] → 汇总输出 YAML
```

## 工作流程

### Step 1: 读取并理解需求文档

**输入**：用户提供的需求文档路径（PDF/DOCX/MD/TXT/HTML）

**操作**：
1. 使用 `read` 工具读取文档内容。若文档格式不支持直接读取（如 PDF、DOCX），使用 `look_at` 工具提取文字内容。
2. 识别以下关键信息：
   - 业务背景与目标
   - 功能模块划分
   - 业务流程与规则
   - 约束条件与边界
   - 角色与权限

**输出**：对需求文档的完整理解，为功能点提取做准备。

### Step 2: 提取功能点

**目标**：将需求拆解为可测试的功能场景。

**操作**：
1. 基于 Step 1 的理解，调用 LLM 提取功能点列表。
2. 每个功能点包含：

| 字段 | 说明 | 示例 |
|------|------|------|
| `name` | 功能场景名称 | "打卡规则配置" |
| `description` | 详细描述 | "管理员可以新增、编辑、删除打卡规则" |
| `related_requirements` | 关联的需求原文 | "管理员可在后台配置打卡规则，包括名称、时间、范围..." |

**拆分原则**：
- 每个功能点应是**用户可感知的一个具体操作**
- 功能场景数量建议 **5-15 个**，覆盖全面
- 典型分类纬度：基础数据维护 → 核心业务流程 → 异常处理 → 报表查询
- 粒度适中：太粗则用例集不完整，太细则管理成本高

**输出**：功能点列表（Python list of dicts），包含 name/description/related_requirements。

### Step 3: 逐功能点生成测试用例（循环）

**目标**：对每个功能点，依次生成测试用例。

**操作**：
对每个功能点，执行以下循环：

```
for each feature in features:
    1. 调用 LLM，传入功能点信息和文档上下文
    2. LLM 返回该功能点的测试用例列表
    3. 累加到结果集
    4. 进入下一个功能点
```

**每轮循环生成规范（每个功能点至少 3 条）**：

| 用例类型 | 说明 | 最低数量 | 典型优先级 |
|---------|------|---------|-----------|
| **正向** | 验证正常业务路径，操作成功 | 至少 1 条 | P0/P1 |
| **负向** | 验证异常输入、错误操作、权限不足 | 至少 1 条 | P1/P2 |
| **边界** | 验证边界值、极限条件、特殊状态 | 至少 1 条 | P2/P3 |

核心功能（用户高频使用的主流程）建议 **5-10 条**用例。

**每条用例的字段结构**：

```python
{
    "id": "TC_001",                # 用例编号，格式 TC_三位数字
    "name": "管理员成功新增打卡规则",  # 用例名称，清晰表达测试场景
    "type": "正向",                 # 用例类型：正向/逆向/边界
    "priority": "P0",              # 优先级：P0/P1/P2/P3
    "preconditions": "管理员已登录企业管理后台",  # 前置条件
    "steps": "点击打卡规则→点击新增规则→填写信息→点击保存",  # 测试步骤，用→分隔
    "test_data": "规则名称=工作日打卡, 打卡时间=09:00-18:00",  # 测试数据
    "expected": "规则保存成功，在规则列表中可见",  # 预期结果
}
```

**LLM 调用提示词模板**：

```
你是一个测试用例设计专家。根据功能点生成测试用例。

功能点名称：{feature.name}
需求描述：{feature.related_requirements}
功能描述：{feature.description}

要求：
1. 每个功能点至少生成 3 条用例：正向×1 + 负向×1 + 边界×1
2. 用例编号格式：TC_001, TC_002, TC_003...
3. 优先级：P0(核心)/P1(重要)/P2(一般)/P3(边缘)
4. steps 字段用 → 分隔步骤
5. 输出 JSON 格式：{{"feature": "{feature.name}", "test_cases": [...]}}
```

### Step 4: 审查测试用例集

**目标**：对生成的完整用例集进行质量检查。

**操作**：
1. 合并所有功能点的用例
2. 检查以下维度：

| 审查维度 | 检查内容 | 操作 |
|---------|---------|------|
| **完整性** | 是否覆盖所有功能点 | 补充遗漏场景 |
| **正确性** | 用例步骤和预期是否合理 | 修正逻辑错误 |
| **去重** | 是否存在重复用例 | 合并冗余 |
| **规范性** | 编号、格式是否统一 | 调整格式 |

3. 调用 LLM 进行审查：

**审查提示词模板**：

```
你是一个测试用例评审专家。审查以下测试用例集。

审查维度：
1. 去重：合并重复用例
2. 补充：补充遗漏场景
3. 修正：修正表述不清或逻辑错误的用例

输出 JSON 格式：
{
  "verdict": "通过/需改进",
  "issues": [
    {"description": "问题描述", "suggestion": "修改建议"}
  ]
}
```

### Step 5: 输出 YAML 文档

**目标**：将最终用例集输出为结构化 YAML 文件。

**输出路径**：用户指定的路径，或默认的 `./output/testcases.yaml`

**YAML 格式规范**：

```yaml
# 文件编码: UTF-8
# 缩进: 2 空格
# 排序: 按功能点名称排序，用例按编号排序

verdict: 通过                    # 审查结论
issues:                          # 审查问题列表，可为空
  - description: "..."           # 问题描述
    suggestion: "..."            # 修改建议
features:                        # 功能点列表
  - feature: 打卡规则配置          # 功能点名称
    test_cases:                  # 用例列表
      - id: TC_001
        name: 管理员成功新增打卡规则
        type: 正向
        priority: P0
        preconditions: 管理员已登录企业管理后台
        steps: 点击打卡规则→点击新增规则→填写规则信息→点击保存
        test_data: 规则名称=工作日打卡, 打卡时间=09:00-18:00
        expected: 规则保存成功，在规则列表中可见
      - id: TC_002
        name: 新增规则时必填项为空
        type: 逆向
        priority: P1
        preconditions: 管理员已登录企业管理后台
        steps: 点击打卡规则→点击新增规则→不填写规则名称→点击保存
        test_data: 规则名称=""
        expected: 系统提示规则名称不能为空，保存失败
```

**写入操作**：
```python
import yaml

output_data = {
    "verdict": verdict,
    "issues": issues,
    "features": features_with_cases,
}

with open(output_path, "w", encoding="utf-8") as f:
    yaml.dump(output_data, f, allow_unicode=True, sort_keys=False, indent=2, width=120)
```

如果没有 `yaml` 库可用，使用以下方式输出：
```python
import json

# 先将 Python 对象转为 JSON，再由 Agent 自行整理为 YAML 格式文本写入
# 或直接输出为格式化的文本内容
```

## 优先级定义标准

| 级别 | 定义 | 响应要求 |
|------|------|---------|
| **P0** | 核心功能，流程中断即阻断发布 | 必须通过 |
| **P1** | 重要功能，影响用户体验但可绕行 | 必须通过 |
| **P2** | 一般功能，边缘场景或少用功能 | 建议通过 |
| **P3** | 视觉/文案/易用性 | 可优化 |

## 全流程集成 Prompt（一次性执行）

若用户希望一步完成，可使用以下完整 prompt 驱动 LLM：

```
你是一个专业的需求分析和测试设计专家。

请根据以下需求文档内容，完成以下任务：

## 任务说明

### 阶段一：需求分析与功能点提取
- 阅读并理解文档内容
- 识别业务背景、功能模块、流程规则和约束条件
- 将需求拆分成5-15个具体的、可测试的功能场景
- 每个功能点包含：name(场景名称)、description(详细描述)、related_requirements(需求原文)

### 阶段二：逐功能点生成测试用例
对每个功能点：
- 生成正向用例(至少1条)：验证正常业务路径
- 生成负向用例(至少1条)：验证异常输入和错误操作
- 生成边界用例(至少1条)：验证边界条件
- 每条用例包含：id(TC_001格式)、name、type、priority(P0-P3)、preconditions、steps(→分隔)、test_data、expected

### 阶段三：审查与输出
- 审查用例集的完整性、正确性和规范性
- 输出 YAML 格式结果

## 输出格式
输出 YAML，包含以下结构：
- verdict: 审查结论
- issues: 问题列表
- features: 功能点及其测试用例
```

## 质量检查清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 功能点数量 | 5-15 个 |
| 2 | 每个功能点用例数 | ≥ 3 条 |
| 3 | 用例类型覆盖 | 正/逆向/边界均包含 |
| 4 | 用例编号 | TC_001 起，连续不重复 |
| 5 | 优先级分配 | P0/P1 用例占比合理 |
| 6 | 步骤清晰度 | 步骤可执行，无歧义 |
| 7 | 预期结果 | 具体可验证，非空泛描述 |
| 8 | YAML 格式 | 合法，缩进正确 |
| 9 | 中文编码 | UTF-8，无乱码 |

## 故障处理

| 问题 | 处理方式 |
|------|---------|
| 文档无法直接读取 | 使用 `look_at` 工具提取文本 |
| 功能点过多/过少 | 检查粒度：过细则合并，过粗则拆分 |
| LLM 返回非 JSON | 尝试重新生成，或手动提取 JSON 部分 |
| YAML 输出乱码 | 确保 file encoding 为 utf-8 |
